## 1. 执行目标、边界和固定技术方案

### 1.1 给执行者的指令

请依据本规格完成开发、测试、离线安装包制作和交付。用户此前确认的需求已经包含在本规格中，无须重新询问已确定事项。

- 新建项目目录：`D:\workspace\codex工作区\local-stock-manager`，不得修改工作区中其他项目。
- 本规格为完整需求基线。遇到依赖问题，应先修复依赖或打包方式，不得自行取消离线识别、二次确认、Excel 导出等功能。
- 不得使用模拟 OCR、随机识别结果、空实现或仅界面原型作为最终交付。
- 不得要求最终用户安装 Python、.NET、数据库、Office，或者配置 API 密钥。
- 不得把待开发、未测试或需要联网的功能描述成已经完成或可离线使用。
- 不部署服务器，不发布到公共网站，不创建额外聊天；在当前任务完成实现和交付。
- 每阶段完成后运行对应检查。发现失败必须修复；受外部条件限制无法验证的项目必须明确记录。

| 项目 | 固定要求 |

## 2. 页面、操作与业务规则

### 2.1 主窗口与货品管理

主窗口设置四个入口：**库存首页、进货、出货、记录查询**；备份恢复放在“设置”中。

启动后直接进入库存首页，无登录页，展示：

`货品名称｜规格｜单位｜店面数量｜仓库数量｜合计数量｜操作`

- 合计为每种货品自己的“店面＋仓库”，只读。
- 支持按名称、规格搜索，支持隐藏停用货品。
- 不显示跨不同单位货品相加的总数量，避免把箱、件等混合统计。
- 提供新增货品和“调整分布”操作。
- 新增货品时填写名称、规格、单位、店面初始数量、仓库初始数量。
- 名称和单位必填；规格可以为空；初始数量默认均为0。
- 名称和规格分别进行 Unicode FormKC 规范化、首尾去空格、忽略大小写后判断重复；数据库建立对应唯一约束。
- 已停用的同名同规格货品不能重复新建，可重新启用。
- 货品建立后不再提供期初数量编辑；名称和规格允许修改但不能与其他货品冲突，单位锁定。
- 有历史记录的货品只能停用，不能删除；历史单据显示当时保存的名称、规格、单位。

新增货品及期初库存必须经过预览和最终确认，在同一个事务中保存。

### 2.2 数量框统一组件

所有可编辑数量都使用相同组件：

`［－］［整数输入框］［＋］`

具体行为：

- 左侧按钮每次减1，右侧按钮每次加1。
- 支持键盘直接输入和粘贴整数。
- 输入未完成时可以暂时为空，但不能提交。
- 不接受小数、负数、科学计数法或其他非整数内容；不得自动四舍五入。
- 到达下限时禁用减号，到达上限时禁用加号。
- 进货、出货、调拨数量范围为 `1～2,147,483,647`，新增明细默认1。
- 期初的店面和仓库数量允许为0。
- 单种货品两处库存及合计均不得超过 `2,147,483,647`；运算使用64位整数并检查溢出。
- 清单中删除货品使用明确的“移除”按钮，不用数量0表达删除。

### 2.3 进货

渠道固定显示“厂家”，不可更改。

支持：

1. 手动选择货品并输入数量。
2. 通过货单照片识别生成待核对明细。

同一张单据可以包含多个货品。同一货品重复添加时合并数量；界面和提交服务都必须执行合并与总量验证。

提交流程固定为：

**编辑清单 → 查看确认页 → 最终确认入库 → 成功回执**

确认页显示：

- 业务类型和渠道。
- 每项货品的名称、规格、单位、进货数量。
- 仓库变更前后数量、店面数量、合计变更前后数量。

最终确认之前不改变库存。确认成功后：

`仓库增加进货数量；店面不变；合计相应增加。`

### 2.4 出货

只允许手动添加货品、输入数量；不提供 OCR 出货入口。

- 渠道必须选择“零售”或“批发”，初始不预选，避免误记。
- 提交流程与进货相同，最终按钮为“确认出库”。
- 确认成功后：`仓库减少出货数量；店面不变；合计相应减少。`
- 必须按合并后的货品总数量检查仓库库存。
- 仓库不足时禁止提交，即使店面有货也不自动扣减或调拨。
- 错误提示同时显示所需数量和仓库可用数量，提示先调整库存分布。

### 2.5 调整店面／仓库分布

从库存首页打开独立“调整分布”窗口，不能直接改写表格中的两个库存值。

窗口包含：

- 货品。
- 方向：“仓库→店面”或“店面→仓库”。
- 数量框。
- 调整前后两处库存及不变的合计。
- “取消”和“确认调整”。

规则：

- 仓库→店面：仓库减N，店面加N。
- 店面→仓库：店面减N，仓库加N。
- 调出数量不能超过来源库存。
- 保存调拨流水，不计入厂家进货、零售或批发统计。
- 未提交的进出货窗口打开期间，禁止另行打开调拨或其他库存修改窗口。
- 确认操作在事务内重新检查库存，不能仅依赖界面校验。

### 2.6 作废单据

仅已生效、未作废的进货／出货单可以作废。期初记录和调拨记录不提供作废；错误调拨通过反方向调拨纠正。

流程：

**打开单据 → 作废 → 展示反向库存影响并填写原因 → 确认作废**

- 作废进货：从仓库扣除原单数量。
- 作废出货：向仓库加回原单数量。
- 店面库存不变，不自动调拨。
- 若任何货品会产生负库存或超上限，整张单拒绝作废。
- 原单保留并标记“已作废”，另存一条当前时间的反向库存流水。
- 作废必须全部成功或全部失败，不能只恢复部分明细。
- 不允许重复作废，不提供“恢复已作废单据”。
- 作废后的重新录入由用户主动进行，不自动生成新单。

### 2.7 通用提交行为

- 每次待提交操作生成唯一提交标识，数据库唯一约束防止重复记账。
- 最终确认后禁用提交按钮，直至返回结果。
- 取消确认页只返回编辑状态；关闭未提交窗口不改变库存。
- 保存失败时保留用户清单，并明确提示未记账。
- 成功后刷新库存和查询结果，并显示单据编号。
- 不允许通过直接编辑数据库余额替代上述业务操作。

## 3. OCR、历史查询与 Excel 导出

### 3.1 图片输入与识别流程

支持 JPG、JPEG、PNG 文件选择或拖入，也支持电脑内置／USB 摄像头预览、拍照。

- 手机照片由用户先复制到电脑；不实现二维码上传或手机网页。
- 支持图片旋转、裁剪、放大查看。
- 一次识别一张图片；同一进货草稿可以继续添加多张图片并汇集明细。
- 保留原图片副本和处理后的图片，均只存本地。
- 无摄像头或权限被拒绝时给出提示，图片导入和手动进货继续可用。

识别处理：

1. 对用户选定的图片执行本地 OCR。
2. 根据表头、文字位置和行列关系提取名称、规格、数量。
3. 表头映射至少支持：品名／商品名称／货品名称，规格／型号，数量／实收数量。
4. “单价”“金额”“总计”“合计”等不能被默认当成货品数量列或明细行。
5. 多个候选数量列无法确定时，要求用户指定数量列；不能自行选择可能错误的列。
6. 展示左侧图片、右侧可编辑明细，并可定位到对应图片区域。
7. 名称＋规格完全匹配时关联已有货品；近似匹配只提供候选，必须由用户选择。
8. 未知货品可以新建；新建时库存为0，照片中的数量仅在最终进货确认后增加。
9. 缺失、非整数、低置信度、身份不明确的字段突出显示。低置信度阈值初始为0.90。
10. 每行须标记“已核对”；有未核对行或无效数量时禁止进入进货确认页。

OCR 失败时不得填入虚构结果；用户可以重试、换照片或手动录入。

### 3.2 OCR 工作程序接口

桌面程序通过标准输入／输出的单行 JSON 与 OCR 子进程通信，不启动 HTTP 服务。

请求包含：

`protocolVersion、requestId、imagePath`

成功响应包含：

`requestId、success、imageWidth、imageHeight、blocks`

每个 block 包含：

`text、confidence、box`

- `box` 为输入图片像素坐标中的四个顶点。
- 失败响应包含稳定错误码及可读错误信息。
- 标准输出只允许协议 JSON；运行日志写入标准错误。
- OCR 进程一次处理一个请求；超过120秒返回超时，可取消并重启工作进程。
- 图片不存在、格式不支持、模型缺失、识别失败必须区分报告。
- OCR 进程只能读取图片并返回结果，不得写库存数据库。
- 货单行列解析、货品匹配和用户确认由桌面端完成。

### 3.3 记录查询

记录查询分为：

- **进出货记录**：用户日常查询和导出的主要页面。
- **库存变动记录**：展示期初、进货、出货、调拨、作废反向流水，便于核对库存。

进出货记录筛选：

- 进货／出货／全部。
- 厂家／零售／批发／全部。
- 货品名称、规格。
- 有效／已作废／全部，默认有效。
- 日期范围，默认今日。

日期使用本机本地日期，并固定如下定义；设今天为 `D`：

| 快捷项 | 开始日期 | 结束日期 |
|---|---|---|
| 今日 | D | D |
| 昨日 | D－1天 | D－1天 |
| 过去7天 | D－6天 | D |
| 上个月 | 上个月1日 | 上个月最后一天 |
| 过去3个月 | D.AddMonths(-3) | D |
| 过去6个月 | D.AddMonths(-6) | D |
| 去年 | 去年1月1日 | 去年12月31日 |
| 自选日期 | 用户开始日期 | 用户结束日期 |

- 开始、结束当天均包含；开始晚于结束时拒绝查询。
- 月份不足对应日期时采用该月最后一天，与 .NET 日期方法一致。
- 超出保留范围的查询显示“仅保留最近5年记录”，不能将已删除记录显示为零发生量。
- 明细默认按发生时间倒序，同时间用单据ID稳定排序。
- 页面每页100条，导出不受分页限制。
- 业务日期取提交时本机日期并保存；之后更改系统时区不能重新划分历史业务日期。
- 首版不允许回填历史业务日期。

### 3.4 Excel 导出

查询和导出必须使用同一份筛选对象与查询服务，不能各写一套日期或状态判断逻辑。

生成工作表：

1. **明细**：单据编号、发生时间、业务类型、渠道、货品名称、规格、单位、数量、状态、作废时间、作废原因。
2. **汇总**：按货品＋规格＋单位＋业务类型＋渠道汇总有效数量。
3. **筛选说明**：筛选条件、生成时间、实际保留起始日期、明细行数。

约束：

- 导出筛选命中的全部记录。
- 已作废原单在选择“全部”或“已作废”时可出现在明细，但永远不计入有效数量汇总。
- 作废反向流水不作为新进货或新销售计入汇总。
- 汇总是“当前仍有效、业务日期位于筛选范围内的单据”，不是历史时点余额。
- 数量保存为数值单元格；货品文本按字符串写入，不能作为 Excel 公式执行。
- 超过单个工作表行数上限时拆分明细表，不能截断数据。
- 使用保存文件对话框；覆盖已有文件需要标准覆盖确认。
- 先生成临时文件，成功后替换目标；失败不得留下被误认为完整导出的目标文件。
- 文件被占用、无权限、磁盘不足时显示可理解的错误。

## 4. 数据一致性、五年清理和安装交付

### 4.1 数据模型与不变量

数据库至少包含下列逻辑实体：

| 实体 | 主要内容 |
|---|---|
| Product | ID、名称、规格、单位、规范化身份字段、启用状态 |
| StockBalance | 货品ID、仓库余额、店面余额 |
| Document | ID、类型、渠道、状态、业务日期、发生时间、提交标识、作废关联和原因 |
| DocumentLine | 货品ID、当时名称／规格／单位、数量、仓库变化量、店面变化量 |
| Attachment | 单据关联、受管图片相对路径 |
| CarryForward | 截止日期、每种货品在截止日前的仓库及店面结转余额 |
| SchemaMetadata | 数据库结构版本和保留规则信息 |

库存流水以单据明细中的两处变化量为依据：

| 类型 | 仓库变化 | 店面变化 |
|---|---:|---:|
| 期初 | 初始仓库数量 | 初始店面数量 |
| 进货 | ＋N | 0 |
| 出货 | －N | 0 |
| 仓库→店面 | －N | ＋N |
| 店面→仓库 | ＋N | －N |
| 作废进货 | －N | 0 |
| 作废出货 | ＋N | 0 |

必须长期满足：

**当前库存余额＝结转余额＋结转日期以来全部库存流水变化量。**

注意：已作废原单的原始流水仍参与该公式，其作用由作废流水抵消。不能因为原单状态变成“已作废”，就从库存重建中忽略原始流水。

其他固定要求：

- SQLite 开启外键，使用 WAL 和可靠同步设置。
- 修改库存使用写事务，在事务内重新校验。
- 原单、库存余额、流水、作废状态在同一事务中变更。
- 使用应用单实例锁，同一数据目录不允许两个实例同时使用。
- 数据访问不得放在 ViewModel 中，统一经过业务服务。
- 不提供任意设置库存余额的公共业务接口。
- 提供可注入时钟，日期计算与清理测试不得依赖真实当天日期。

### 4.2 五年清理算法

设保留起始日期为：

`C＝本机今天.AddYears(-5)`

保留业务日期 `>= C` 的记录；删除业务日期 `< C` 的记录。

执行时机：

- 启动后、主界面开放写操作前。
- 软件运行跨日后，在无库存写事务执行时。
- 恢复备份后、展示恢复数据前。

执行顺序必须是：

1. 获取维护锁，暂停新的库存提交。
2. 读取上次结转余额。
3. 将本次过期流水的仓库、店面变化量累计进结转余额。
4. 更新结转日期，删除过期单据和明细，在同一事务中提交。
5. 校验清理前后当前库存余额完全一致。
6. 删除已失去有效引用的受管图片。
7. 恢复正常操作。

- 不得简单删除历史后从剩余流水重算当前库存。
- 重复执行同一天清理必须无额外影响。
- 原单过期但其作废流水仍在保留期内时，保留作废流水及自身货品快照；关联原单允许显示“原单已过保留期”，不能级联删除作废流水。
- 数据库事务失败则完整回滚，不得先删图片。
- 图片删除失败记录重试，下次启动继续清理。
- 所有自动删除仅针对应用数据目录内的受管文件，禁止删除用户导入的原照片。
- 货品档案、当前余额和必要结转不受五年删除限制。
- 软件关闭期间不安装后台清理服务，下次启动补做。

### 4.3 本地目录、备份和恢复

固定使用：

- 程序：`%LOCALAPPDATA%\Programs\LocalStockManager`
- 数据：`%LOCALAPPDATA%\LocalStockManager\Data`
- 日志与临时文件：应用自己的独立子目录。

数据库与图片不得放在安装目录，也不得依赖当前工作目录。

手动备份：

- 用户选择目标位置，生成包含数据库、有效附件、结构版本和清单的备份压缩包。
- 使用 SQLite 备份 API，不能直接复制可能包含未合并 WAL 的数据库文件。
- 备份期间保持数据库与附件的一致快照。
- 不提供云备份或自动联网传输。

恢复：

- 明确提示恢复会替换当前本机数据。
- 先解压到应用临时目录，拒绝越界路径。
- 检查数据库完整性、版本兼容、库存不变量和附件清单。
- 在临时副本执行必要迁移和五年清理。
- 校验成功后关闭连接并切换数据目录；失败恢复原目录，不能破坏现有数据。
- 不支持把多个备份合并为一份库存。

用户导出的 Excel 和手动保存的备份由用户管理，不在软件自动删除范围内。

### 4.4 安装与升级

- `.NET` 使用 `win-x64` 自包含发布，不使用需要目标机器联网安装运行时的模式。
- 随包提供 OCR Python 运行环境、ONNX 模型、词典、图像处理及其他必要原生依赖。
- 所有启动路径均从程序目录或数据目录解析，不能引用开发电脑绝对路径。
- 安装默认按当前用户执行，无须管理员权限。
- 创建开始菜单入口，可选桌面快捷方式。
- 新装首次启动自动建库。
- 升级先做结构迁移保护，迁移失败保留原数据并提示；不能重新建空库掩盖错误。
- 卸载默认保留用户数据。
- 首版不包含自动更新和代码签名；如未签名，应在交付说明中说明 Windows 可能显示未知发布者提示。

安装包必须在断网状态下完成安装和首次 OCR。仅在开发机运行成功不算满足“开箱即用”。

## 5. 实施顺序、验收矩阵与交付标准

### 5.1 实施顺序

必须按以下顺序推进，每一步都有可运行结果：

1. **建立项目和技术可行性验证**：WPF 自包含运行、SQLite 事务、独立 OCR 返回真实中文结果、Excel 导出、NSIS 打包；尽早验证离线依赖完整性。
2. **实现业务内核**：货品、期初、进出货、调拨、作废、提交去重及库存一致性测试。
3. **完成手动操作界面**：统一数量框、库存首页、清单、确认页和记录详情。
4. **接入真实 OCR**：导入、摄像头、图片处理、列选择、货品匹配、逐行核对、进货确认。
5. **完成查询与导出**：统一筛选模型、全部日期选项、分页、Excel 明细与汇总。
6. **完成数据生命周期**：五年结转清理、备份恢复、结构迁移。
7. **制作最终安装包并验收**：在干净 Windows 11 x64 环境验证，整理交付文件。

不得把 OCR 打包和五年清理留到全部界面完成以后才验证。
